# How the sandbox works

This module builds and runs a disposable container image for each agent. See
the [root README](../../docs/index.md) for usage; this file explains the
implementation.

## Image build (`builder.py`)

On the flake path the **flake is the source of truth for the environment**:
each agent's `flake.nix` defines a `dockerTools.buildLayeredImage` `image` output
whose `contents` are
`[pkgs.bash pkgs.git pkgs.coreutils pkgs.cacert <agent> links fhs-libs] ++
(import ./extra-packages.nix { inherit pkgs; })` — coreutils gives the thin
runner layer a POSIX userspace (`mkdir`/`cat`/`chmod` for its RUN steps and the
entrypoint) and cacert a CA bundle (dockerTools images have no system CA store,
so `SSL_CERT_FILE` and `HOME=/root` are set in the image `config.Env`). The image
`config` also sets the Cmd/Entrypoint/WorkingDir. `extra-packages.nix` is generated by agent-pod from the
config's `flake.extra_packages` (so adding a tool is just config), and a `links`
derivation installs a stable `/usr/local/bin/<agent>` symlink for the runner.
The generated Dockerfile is a **thin runner layer** only — it adds the git
identity, bakes an **entrypoint** that checks out the session's ephemeral git
worktree (`agent-pod-entrypoint`, see Run below) and execs the agent CLI, and
(pi) the baked settings.json + extension installs. What is *installed* is
decided by the flake, not the Dockerfile.

### `extra_packages`

`extra_packages` takes **raw nixpkgs attribute names** (`uv`, `nodejs_22`,
`python311`), not version strings or package names — the flake's locked nixpkgs
input is the source of truth. Every entry is added to the image's `contents`
(the `++ extra` in the flake), so its `bin/` lands on the image's `/bin` via
dockerTools' buildEnv merge. Two settings control nixpkgs' safety gates:

- `allow_unfree` (default `false`) — nix refuses to evaluate packages with
  unfree licenses (e.g. `unrar`); opt in explicitly to install them.
- `permitted_insecure` (default `[]`) — nix refuses to build packages with
  known vulnerabilities; **default-deny** because this is an agent sandbox that
  executes potentially untrusted code. Allow the exact version string, e.g.
  `permitted_insecure: [openssl-1.1.1w]`.

Both map into a generated `flake-config.nix` (only non-default keys are emitted,
so a flake's own required config — e.g. claude's `allowUnfree` for the unfree
`claude-code` binary — is never overridden). Before building, agent-pod runs a
cheap nix eval in the builder container to classify each name
(unknown / insecure / unfree / ok) and fails fast with an actionable message
instead of a cryptic nix build error.

**FHS loader shim.** nix binaries carry a patched ELF interpreter into the
store, but tools that download their own glibc runtimes at use-time — `uv`,
`pnpm`/`corepack`, `rustup`, `deno` — exec them via the standard
`/lib64/ld-linux-x86-64.so.2`. Each flake ships an `fhs-libs` derivation
symlinking `${pkgs.glibc}/lib/ld-linux-x86-64.so.2` to that standard path, so
`uv run python` works in the image. **User-supplied flakes (option 1) must
include the same shim** or uv-downloaded runtimes will fail to exec.

### Caching

Building the flake image needs no host Nix: nix runs inside the `nixos/nix`
builder container (`podman run`), and the resulting image tarball is loaded with
`podman load`, then the thin layer is `podman build`-ed `FROM` it. Caching:

- **Persistent named-volume nix store** — the nix store lives in the named
  volume `agent-pod-nix` (mounted at `/nix`, shared by all agents), so rebuilds
  fetch only the delta from cache.nixos.org — e.g. adding `gnumake` to
  `extra_packages` fetches just gnumake, and switching agents reuses the shared
  closure. A named volume keeps store I/O in the container runtime's native
  filesystem instead of crossing the host-sharing layer (fast in virtualized
  runtimes). The `nixos/nix` image's own `/nix` is copied into the volume on
  first use (podman's copy-on-first-mount), keeping `nix` itself runnable. Nix
  manages store validity itself — no hand-rolled `cp`/`--load-db`.
- **Skip when unchanged** — `build_image` hashes the thin Dockerfile + baked
  settings + `flake.nix`/`flake.lock`/`extra-packages.nix`; a matching hash with
  an existing image skips the rebuild entirely.

A flake.lock bump changes the agent's inputs and correctly refetches the delta.

## Files, state, and instructions (`runner.py`)

**One generic concept** supplies every file/dir to the sandbox: the agent
config's `files` list. Each entry (`FileMount`) has a host `source` (or a
`builtin:` generator), a `name` mounted at `<container_home>/<name>` by default,
`permissions` (`ro`/`rw`), and an optional `description` shown by `ap plan`.
Mount order follows list order, so a directory entry before a file nested
inside it wins for that exact path (e.g. the host skills dir before the
runner-authoritative git-workflow `SKILL.md`).

Kinds of entry:

- **Host mirror (read-only)** — a host path mounted `ro` so the sandbox always
  reflects the host with no stale seeded copy. Declared as
  `{source, name, permissions: ro}`; skipped when the host path is missing
  (silently when `optional: true`, otherwise a warning). This replaces the old
  `host_mounts` and the `skills_dir` passthrough (`~/.agent/skills` → each
  agent's global skills dir).
- **Generated (`builtin:`)** — content agent-pod writes at runtime instead of
  mounting from the host:
  - `builtin:instructions` — the global instruction file (`AGENTS.md` /
    `CLAUDE.md`) generated by the runner and mounted at its entry's container
    path. Its body points the agent at the `builtin:git-workflow` skill path
    (when present) and `@`-references any `--context-file` files.
  - `builtin:git-workflow` — the git-workflow skill (`prompts/git-workflow.md`)
    mounted into the agent's skills dir, loaded on demand (progressive
    disclosure). Each agent's instruction file points the agent at it.
- **Writable state** — `{name, permissions: rw}` entries whose state lives in
  the session state dir under `~/.config/container-agents/<agent>/` (or
  `<agent>/<session>/` for named sessions) and are mounted `rw` into the
  container. A `seed: true` entry copies its host `source` into the state dir
  on first run and mounts the copy, so the host file is never modified
  (pi's `auth.json`, opencode's `auth.json`); `secret: true` flags the mount
  `[secret]` in `ap plan`. A `--settings-file` supplied on the CLI overrides
  the seed for `settings.json`. A writable entry with no source is created
  empty (`{}` for JSON) or as a directory (inferred, or explicit via `type`).
  This replaces the old `persist_files`, `persist_dirs`, `seed_files`, and
  `credential_file`.

Writable-state entries are created by `ensure_host_paths` and cleaned up by
`ap sessions <agent> --rm <session>` (via `AgentConfig.writable_state`). The
read-only host mirrors are identical across sessions since they always mirror
the host.

In a user config (global or project), `files` is **appended** to the bundled
agent's list (`get_effective_agent_config` in `loader.py`) rather than
replacing it, so a user can add their own file/dir entries without dropping the
agent's built-ins.

## Plan (`plan.py`)

`ap plan <agent>` builds the same mount list as the runner (`build_mounts` in
`runner.py`), so it always reflects what will actually run, and renders it as a
permission screen. Filesystem access lists each host path with its `read-only`
/ `read/write` mode and the container path it maps to, grouped by access type
(read/write first, then read-only, then tmpfs); write access is shown in red,
as is broad read-only scope like `~` or `~/.config`, and credentials are
flagged `[secret]` in red (values never shown). Since env passthrough is
opt-in, the environment section shows only agent-pod's internal vars plus any
`passthrough_envs` you configured, with a live forwarded/not-forwarded status
and `[secret]` on secret-looking names. A final NETWORK & CAPABILITIES section
states the sandbox's network and capability posture, driven by the runner's
actual flags (currently none, so it truthfully reports full outbound network
and podman's default capabilities — see `SecurityProfile` in `runner.py`).

## Run (`runner.py`)

The container is launched with `podman run --rm -it` and allowlisted
environment variables passed through; `--stop-timeout 0` makes podman's own
stop path kill the container immediately (SIGKILL) rather than waiting the
default 10s.

Two repo modes, selected by the user config's `ephemeral` field:

- **Ephemeral (`true`, inside a git repo with at least one commit):** the host
  repo's **`.git`** is mounted read-write at `/repo/.git` (not the working tree)
  and four internal env vars are set — `AP_BRANCH=agent/<profile>/<session>`,
  `AP_BASE=<host HEAD commit>`, `AP_REPO_GIT=/repo/.git`, and
  `AP_WORKTREE=/sandbox/<instance>` (the per-session worktree path). The baked
  `agent-pod-entrypoint` then runs
  `git --git-dir=/repo/.git worktree add -b $AP_BRANCH $AP_WORKTREE $AP_BASE` on
  first run, falling back to `... worktree add --force $AP_WORKTREE $AP_BRANCH`
  when resuming a session whose branch already exists, and execs the agent from
  inside that worktree. Because each session's worktree is a distinct subfolder
  of `/sandbox`, concurrent sessions on one repo never collide on a shared path,
  and a crashed session's leftover registration never blocks a fresh one. The
  container owns the worktree, so every git path it writes is a container path
  — the broken host-path pointer problem is gone. **Only committed files ever
  reach the host**: uncommitted/untracked work stays inside the pod. On exit
  `run_agent` runs a best-effort
  `git worktree remove --force $AP_WORKTREE` so only this session's registration
  is dropped from `.git` — other live sessions' worktrees are left alone; the
  `agent/<profile>/<session>` branch itself stays for review.
- **Direct (`false`, or not a git repo / no commits):** the working directory
  is mounted at `/sandbox` as before; no `AP_*` env, the entrypoint runs the
  agent directly.

`run_agent` does **not** `exec` podman; it runs it as a child process and
traps `SIGHUP`. `--rm` only removes the container when it exits on its own, so
when the terminal is torn down — e.g. a zellij pane running the agent is closed
— a TUI agent (opencode keeps a background server) can survive and keep the
container alive, consuming memory. On `SIGHUP` agent-pod force-runs
`podman stop -t 0` then `podman rm -f` on the instance, so closing the pane
always frees the container.

## Security and credentials

- **Env passthrough (opt-in)** — no environment variables are forwarded by
  default, so `ap plan` never lists a wall of unused API keys. If an agent needs
  one, add `passthrough_envs` to your own config (project or user layer), e.g.
  `passthrough_envs: [MY_API_KEY]`; every listed variable must be set in the
  launching shell or `ap run`/`ap shell` refuses to start (listing the missing
  ones), then injects each via `-e`. This is a deliberate
  trade-off for a local dev tool: the agent process can read those keys. For
  workloads where agents must never hold credentials, see the
  credential-brokering architecture in
  [`adr/001-credential-brokering-architecture.md`](../../../adr/001-credential-brokering-architecture.md).
- **Forwarded vars vs. persisted credentials** — a passthrough var must be set
  in the shell that launches `ap`, or launch fails with the missing names. If a
  model is
  configured with `apiKey: "$MY_API_KEY"` but the var isn't set at launch, the
  model stays unauthenticated. For a login that does not depend on the launch
  shell, store the key in the persisted `auth.json` instead (auto-seeded from
  the host).
- **opencode auth** — opencode authenticates using its own `/connect`-style
  credentials stored in `~/.local/share/opencode/auth.json`. The runner persists
  and auto-seeds that file from the host, so the sandbox is already logged in:
  run `/connect` on the host once and every sandbox inherits the credential.
  This is the reliable path; avoid binding `apiKey` to an env var, because when
  the env var isn't forwarded opencode silently sends an empty `Authorization`
  header.
- **`.gitconfig`** — a `safe.directory = *` entry is written for the container
  root user so git works on the mounted repo.
